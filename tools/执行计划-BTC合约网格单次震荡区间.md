# 执行计划：BTC 合约网格单次震荡区间

## 1. 需求理解

### 1.1 用户原始需求

> 给 BTC 合约做多、做空网格增加震荡区间上下界和区间内每格保证金，参数默认 `-1`。挂单时处于区间内，使用区间保证金。离开后上下界变为 `-1`，再次进入也使用原保证金。其他网格逻辑保持原行为。

### 1.2 我的理解

两个 BTC 入口各自传入三个参数，现有 `margin_amount_per_order` 仍是常规每格保证金。新配置启动时若现价在区间外，先等待现价首次进入，再启用区间。启用后，以**每张新开仓单的网格委托价**判定使用哪档保证金，区间内用新区间保证金，区间外用常规保证金。同一轮可同时出现两档金额。进入和离开由市场现价判断，上下界均包含在内。首次观察到现价离开时，区间永久失效。

### 1.3 实现目标

- 两个入口和对应的 `run_grid`、`run_short_grid` 均支持传入上下界和区间每格保证金。三个参数默认为 `-1`。
- 由市场现价推进区间状态，由网格委托价逐笔选择保证金。离开后把运行时有效上下界设为 `-1`。建议将失效记录写入数据库，使 `resume` 后相同配置仍保持失效。
- 新保证金只影响**新创建的开仓单**。已挂开仓单和已成交仓位保留原数量，原有止盈单与订单维护规则继续执行。

### 1.4 非目标范围

本次范围是两个 `BTC_USDT` 入口及其通用合约程序的可选能力。币本位入口、杠杆模式、止盈计算、参考价、格距、挂单数量、原网格撤单和对账规则均沿用现状。运行时不写回 Python 入口文件。

## 3. 总体实现方案

两个 BTC 入口支持 `range_lower_price="-1"`、`range_upper_price="-1"`、`range_margin_per_order="-1"` 和 `range_revision=1`，默认关闭。开启时，保证金和价格均以 `Decimal` 处理。两个 USDT 永续入口的每格保证金均以 USDT 计。

例如，在需要启用的 BTC 入口中修改以下参数，其他参数保持原值：

```python
startup_mode="resume",
range_lower_price="70000",
range_upper_price="71000",
range_margin_per_order="3",
range_revision=1,
```

1. 参数全部为 `-1` 时走常规保证金。开启时要求价格上下界均为正数、下界小于上界且区间保证金大于零。缺参、混用 `-1`、非有限数值或倒置边界时在任何私有交易操作前报错。
2. 新配置从「等待进入」开始。在首次观察到市场现价位于闭区间 `[下界, 上界]` 前，所有新开仓单使用常规保证金，即使某张委托价已经在区间内。首次观察到现价进入后启用区间。
3. 区间启用后，逐笔比较新开仓单的委托价。`下界 <= 委托价 <= 上界` 使用区间保证金，其他委托用常规保证金。首次观察到现价严格越界时，先持久化「已失效」，把运行时有效上下界置为 `-1`，越界当轮起所有委托使用常规保证金。
4. `resume` 加载同一配置的记录。已失效的配置在价格回到区间内时仍用常规保证金。这一状态独立于工作副本参数值、活动订单是否为空和生成的策略码。
5. 将该轮区间状态和价格选档规则接入当前方向的开仓计划函数，在逐笔计算张数前选出保证金。沿用原张数精度、限额和原子占位。多空各自完成接线，公共部分限于参数校验、单次状态转换、按委托价选档和数据库存取等原子能力。

## 4. 详细执行步骤

### 步骤 1：添加参数和校验

**执行目标**是在两个入口提供明确配置，兼容现有调用。

**具体操作**

1. 在 `run_grid`、`run_short_grid` 现有参数末尾追加三个区间参数和一个正整数轮次参数，均为可选关键字参数，避免改变已有位置参数的含义。
2. 在两个 BTC 入口传入三个 `-1`，添加单位注释。保留多头 `1.9`、空头工作副本 `1` 的常规保证金。
3. 识别全 `-1` 禁用配置后，再校验开启配置的 `Decimal` 和正值。现有 `core.decimal_value` 只接受正数，所以先识别哨兵值。

**涉及文件 / 模块**为两个 BTC 入口、两个通用合约模块及参数校验。

**输入**为三项配置和现有常规保证金。**输出**为禁用状态或已校验的上下界及区间保证金。

**完成标准**为缺省调用兼容，错误配置在交易操作前被拒绝。

**本步骤验证方式**

1. 静态检查两个入口调用及已有调用签名。缺省时应保持原保证金和原参数顺序。
2. 用全 `-1`、有效配置、部分填写、上下界相等和倒置、`NaN`、无穷值分别驱动校验。仅前两类成功。

### 步骤 2：保存一次性状态和恢复规则

**执行目标**是让已消费区间在同配置重启后保持失效。

**具体操作**

1. 先完成步骤 1。在 `GridStore` 迁移中新增 `futures_range_state` 表。`market` 包含结算币种与多空方向。按 `market`、`currency_pair`、`grid_tag` 标识策略，以规范化后的原始上下界和 `range_revision` 区分轮次，保存状态和更新时间。稳定的标识可以在活动订单为空或生成的策略码变化时读回。保留各组边界和轮次记录，避免切回旧配置时复活已失效区间。
2. 用已保存的状态推导有效上下界。失效时两者均为 `-1`。保留原始配置值以识别重启时是否为同一组上下界。
3. 仅在「等待进入 → 区间内」与「区间内 → 已失效」等真实变化时提交状态。未用过的边界或轮次从等待进入开始。仅调整每格保证金或重启服务不重新激活相同边界和轮次。关闭选项时保留已失效记录。
4. 实盘在已有进程锁下恢复状态。区间状态使用独立存取逻辑，`startup_mode="reset"` 沿用原订单重置流程，并且同一组已失效边界仍可从新表读回。行情获取失败时不推进区间状态。若状态写入失败，在内存保留已观察到的转换，跳过新增开仓，下一轮先重试写入再继续选档。止盈维护走原线程。

**涉及文件 / 模块**为 `GridStore`、两个合约程序的启动路径和临时 SQLite 测试。

**输入**为策略标识、区间配置、成功读取的现价及旧状态。**输出**为新状态、有效上下界和可供后续读取的记录。

**完成标准**为同一策略失效后重启仍失效，多空隔离，既有周期与布局记录保持原值。

**本步骤验证方式**

1. 用无新区间表的临时旧库启动，检查新表出现且原有订单、数量、止盈价保持原值。
2. 分别模拟进区间、越界后关闭数据库再打开、无活动周期时改常规保证金，以及改变 `grid_step_pct`。相同震荡上下界下不重新激活。
3. 在同一临时库分别写多空状态，多头越界时空头仍可使用区间金额。模拟写入失败，确认不执行本轮新增开仓。

### 步骤 3：在多空开仓路径使用选定保证金

**执行目标**是只改变新开仓计划的张数来源。

**具体操作**

1. 依赖步骤 1、2。在 `run_grid` 和 `run_short_grid` 的各自主循环中紧接现价读取更新区间状态。分别为 `desired_buy_orders`、`desired_short_orders` 增加可选的按委托价选档参数，保留原 `margin` 作为默认金额。先生成网格价，再按每笔委托价选择保证金，并调用现有 `calculate_contract_size`。
2. 把区间状态更新置于资金冷却检查之前。即使账户资金不足、该轮没有空格、成交前没有发送订单，也能识别离开区间。模拟两次轮询之间越界又回归的情况时，按实际观察到的价格序列解释，仅有区间内快照不能判定越界。
3. 处理启动计划。目前两边在打开数据库前就计算一次计划。参数禁用时沿用原校验路径。启用时，预览用公开现价判断新配置是否触发，再逐笔按委托价选择保证金。实盘先在已有进程锁下恢复状态，并使用新读到的行情完成开仓张数预检，再设置杠杆、启动对账和止盈线程。实盘首批下单仍由主循环依据当轮状态和委托价决定，预览不更新持久状态。
4. 开关生效与失效时输出一次现价、方向和切换的每格保证金。原有补单仍检查同格占位，原有撤单规则仍按有效网格维护。

**涉及文件 / 模块**为两个通用合约模块的预览和主循环，以及现有张数计算函数。

**输入**为现价、区间状态、每笔委托价、两档保证金和现有网格参数。**输出**为逐笔选档后的开仓计划及必要的切换日志。

**完成标准**为多空两边的预览与下单路径都已接线，已有挂单数量、止盈、对账与下单方向保持原逻辑。

**本步骤验证方式**

1. 模拟两边现价 `69000 → 70000 → 70500 → 71000 → 71001 → 70500`，区间设为 `[70000, 71000]`。首轮全用常规金额，进入后到越界前按每笔委托价选档，最后两轮全用常规金额。在现价 `70500` 的首次区间内轮次，构造多头委托 `69999.9、70000、70499.9` 和空头委托 `70500.1、71000、71000.1`，预期多头依次选常规、区间、区间金额，空头依次选区间、区间、常规金额。
2. 预放一笔已挂开仓单和一笔已成交带止盈单，在区间进入和退出两侧检查相同订单 ID 和数量。模拟退出时仍在余额冷却，确认之后下一个可下单轮次使用常规金额。

**涉及文件 / 模块**为新增测试、现有合约和恢复测试，以及两个 BTC 入口。

**输入**为完整补丁与第 5 节模拟数据。**输出**为离线验证结果和预览日志。

## 5. 整体功能验证方案

### 5.1 正常流程验证

在临时数据库中分别运行多头和空头模拟。将两个方向的常规保证金各设为入口原值，区间保证金设为 `3 USDT`，设定区间 `[70000, 71000]`，使用第 4 节给出的行情序列。校验两边传入张数计算的实际金额，以及每个开仓单最终的数量。确认越界前已发出的委托保留，后续回到区间使用原金额。

### 5.2 异常流程验证

| 异常场景 | 验证方法 | 预期结果 |
|---|---|---|
| 参数非法或不完整 | 用负值与正值混合、倒置边界、非有限数启动 | 验证失败，不执行私有操作 |
| 行情查询失败 | 模拟超时或无效价格 | 不修改区间状态，按原异常机制处理 |
| 离开时状态写入失败 | 模拟 SQLite 写入异常，下一轮价格已回区间 | 该轮不开新单，止盈维护可继续，写入恢复后先保存已观察到的失效，再恢复常规下单 |
| 区间金额低于最小下单要求 | 模拟会取整为 0 的张数和超过最大张数的情形 | 沿用既有数量校验，错误可辨认，没有不合法下单请求 |

### 5.3 边界条件验证

| 边界条件 | 验证方法 | 预期结果 |
|---|---|---|
| 现价等于任一边界 | 分别输入 `70000` 和 `71000` | 都视为区间内 |
| 从上／下侧越界 | 进入后分别测试 `71000.1` 与 `69999.9` | 越界当轮即失效，重进仍用常规金额 |
| 启动现价在区间外，但某笔委托价在区间内 | 模拟下方启动时的开空委托，或上方启动时的做多委托 | 区间等待触发，区间内委托也使用常规金额。现价首次进入后才逐笔选档 |
| 现价在内，同一轮有区间内外委托 | 生成跨边界的一组订单，包括恰好命中边界的委托 | 仅区间内及边界委托用区间金额，区间外委托使用常规金额 |

### 5.4 数据一致性验证

记录模拟前后的 `grid_cycles`、`grid_layouts` 与新区间状态，对比变更前后的历史订单 ID、价格和数量。打开新表后验证按市场、交易对和策略隔离。测试失效记录正常写入和重启读回，迁移只新增表，运行时自动失效不会删除旧状态。

### 5.5 状态一致性验证

在首次进入后重启、失效后重启和冷却期间越界三种条件下，逐轮比较数据库、运行时有效上下界、日志和实际挂单计划。初次进入的记录用于恢复区间，失效后的有效上下界始终为 `-1`。没有前端界面，调用入口与日志是用户核对状态的方式。

### 5.6 回归验证

保持三个参数默认 `-1`，对比多空两边的价格、名义金额、张数、`reduce_only`、止盈窗口、同格占位、资金不足冷却和关闭线程顺序。另测普通修改保证金后的 `resume` 与间距修改触发的止盈重排。选档不会改变已有订单的恢复规则。

## 6. 测试用例建议

| 测试类型 | 测试内容 | 验证目标 | 预期结果 |
|---|---|---|---|
| 单元 | 参数默认禁用、合法组合、非法组合 | 保证兼容和配置可诊断 | 同步断言是否启用及错误原因 |
| 单元 | 等待、按委托价逐笔选档、越两个边界、重新进入 | 区间仅触发一次，选档按委托价 | 触发前统一用常规金额，触发后按委托价比较，失效后上下界为 `-1` |
| 集成 | 多空端分别生成实际下单请求 | 检验消费了选定的金额 | 数量按步长取整，方向和止盈逻辑沿用原规则 |
| 集成 | 旧库迁移与同配置 `resume` | 状态持久化和订单兼容 | 旧记录可读，失效状态不会丢失 |
| 端到端 | 模拟价格、成交、资金冷却和重启 | 验证真实脚本调用顺序 | 未确认成交和运行时状态由原流程处理，不因区间切换重下旧单 |

## 7. 风险点

| 风险 | 影响 | 规避方式 | 验证方式 |
|---|---|---|---|
| 市场价格在两次轮询间短暂越界，或离线期间越界后返回 | 程序不会感知这次越界 | 明确按成功读到的行情判定，使用现有轮询周期 | 模拟行情序列和断线恢复 |
| 用动态保证金参与策略识别或布局重排 | 运行中的周期可能错配或被重新定价 | 仅在计算新开仓计划时选档，单独保存区间状态 | 修改金额和格距后对照两类状态及订单 ID |
| 多空共享行情但状态混用 | 一边失效会影响另一边 | 区分结算币种、交易对、方向、策略标签，保留现有锁 | 多空共享临时库的隔离测试 |
| 新状态表上线及并发写入 | 旧数据库升级、写锁争用和启动恢复异常 | 新增表并复用已有 SQLite 锁和事务，仅状态改变时写入 | 旧库迁移、写锁失败和再次启动用例 |
| 实际下单数量增大或取整为零 | 资金不足或开仓请求失败 | 沿用张数上下限、余额不足处理和日志，先用离线价格样本检查金额 | 测试最小张数、最大张数及资金不足 |
| 实盘配置及行情变化 | 模拟测试覆盖不到交易所即时成交顺序 | 部署时核对同步版本，使用预览验证选档和金额 | 对照预览日志与离线模拟的预期，不声称已验证实盘 |

## 8. 更换区间与重新启用

- 更换到未用过的价格上下界，保留 `startup_mode="resume"`，按新区间等待首次进入。
- 继续原区间：保持价格上下界和 `range_revision` 不变，重启后恢复原状态，单独改保证金不会重新开启。
- 要用相同边界开启新一轮，改用未用过的 `range_revision`（例如 `1` 改成 `2`），再以 `resume` 重启。不要为了开启新一轮而重置订单库。

## 9. 建议执行顺序

1. 定义参数和边界规则，通过签名兼容和参数校验测试。
2. 完成 SQLite 状态迁移和失效恢复，通过旧库、多空隔离与重启测试。
3. 分别接入多头和空头的预览、实盘计划与日志，通过资金冷却和挂单回归。
4. 运行离线整体验收及双入口预览，再交付同步文件。

## 10. 最终交付标准

- BTC 多头和空头入口均可启用或关闭单次区间，默认 `-1` 时原调用兼容。
- 新配置启动时在区间外则等待触发。现价进入后，仅委托价在区间内的新开仓单使用区间保证金。首次观测到现价离开后，有效上下界为 `-1`，再次进入和相同配置重启均使用常规保证金。
- 旧订单、持仓数量、原撤单规则和止盈逻辑通过回归验证。状态存取、错误提示及区间切换日志符合计划。
- 步骤级测试和整体价格序列验证均通过，两个入口可离线模拟预览。
